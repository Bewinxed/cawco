# Component canvas

The canvas is the project's real component, mounted live by the project's own toolchain in every state its code reaches: each story of its **states file** (`<Component>.stories.ts`, CSF 3, beside the component) is a frame, and each frame is drawn again in every interaction state its CSS has a rule for (hover, focus, pressed), derived, never authored. You see what you drew: the canvas page reports every frame to the stage, and every tool answers from that **report**, never from the files alone. The `show` skill's step 1 comes first. The canvas is your **working drawing** and reaches no one else: a choice the person must make reaches them on a decision page (the `decision-page` skill) whose options `Preview` your stories, and a whole surface reaches them as a preview at its path.

## Steps

1. **Read the map.** `design_map` with `dir` (or `query`) for the folder you build in; `component` for any part you might use. Done when you know which existing components this one is made of: you **mount** those; their markup stays theirs (`references/map.md`). On a clean-slate redesign the surface being replaced is out of the map: mount only the design system's primitives and write every part above them new.
2. **Write the component** props in, events out: everything a state needs arrives as a prop, so every state can be forced from a story. The component follows its props while mounted: a story's args are inputs the live instance takes at any time, never a record it copies into its own `$state` as it opens (the `house/follows-props` lint catches the copy). Done when its build and type-check pass.
3. **Write the states file** beside it:
   - `export default { title: "Group/Name", component, args }` with what every story shares; `title` is the section's heading.
   - **Each state is a situation** the person meets that the code reaches: one export each, named as the product talks (`Waiting`, `Denied`), with only the args it changes. Each draws a picture none of the others draws; two that draw alike are one state, so keep one. Keep the few that help him judge (the result at rest, the empty, the longest, the failure he recovers from) and leave out a branch he would not tell from another.
   - **The label is what he would say**: a one-line doc comment above each, the sentence he would say looking at that frame, `/** Waiting for the phone to scan the code. */`. It names the situation in his words: no prop, export or field names, no list of what is on screen, no width. It is the frame's label.
   - **A store the component reads is the story's own**: a story puts a store module (the board, the hub's socket) in its state by importing it inside its `beforeEach` and writing it through the store's own writers, `async beforeEach() { const board = await import("./stores/board.svelte"); board.holdMachines(machines); }`. That story runs in a module runner of its own: its runner evaluates the states file, the store, and every module between them, and takes every other module from the page, so each story of one file holds its own value on one page and the store's derived views read what was written. The component stays as it is, and a renamed writer fails the type check. The stage runs each `beforeEach` (the meta's, then the story's) once as the section loads, before any frame mounts, and again with a fresh runner after every edit to a file the section draws from. The seed must reach the component: import the store the component reads, never a helper that imports it, or the frame is refused and says so. A static import of a store is the one store every frame shares, and the lint refuses it in a states file; `import type` is free.
   - **A store read through a provider** (Pinia, Jotai, a React or Svelte context) is given by a decorator per story, never seeded in `beforeEach`: the decorator makes the store's instance and provides it, as the app's root does, and the story's `beforeEach` writes that instance.
   - **The frame is its container**: the stage draws the story's root against its frame's edge, so a part that lives inside a padded surface in the product (a row in a list, a chip in a bar, a card's body) is mounted in that surface, with that surface's padding, through the story's `decorators` or a fixture beside it. A whole surface brings its own.
   - **The width is the canvas's**: the panel draws every story at the widths he picks, so one state is one story at every width. A piece with one production width (a phone sheet) names it once, as the meta's `parameters: { viewport: "phone" }` (or `"tablet"`, `"desk"`, a width).
   - A flow between states: `from: "Waiting"` and a `play` on the destination story that calls `update`, so the live instance moves and its own motion plays (`references/moves.md`).
   - **The poster**: the canvas opens on the frame that tells the story on its own, the result on screen and at rest, never mid-move; it is the first export. A `steps` sequence names its payoff step.
   - **The beats**: `steps`, or a chain of `from`, is three to five states and a payoff, in the order the person meets them; more only when they clarify.
   - **A provider the app's root gives its tree** (a tooltip provider, a theme) goes in the project's `.storybook/preview.*`, whose decorators wrap every story outside its own (the dashboard's `apps/dashboard/.storybook/preview.ts`), never in each states file's decorators. A page-wide singleton, such as the dashboard's lightbox, stays out of both: one round each story opens one per drawing.
   Done when every state from the brief is one export with its sentence, the first export is the poster, and the build passes.
4. **Open the canvas**, to yourself. `artifact_create({ kind: "component", name, title, does: "judge", ask, file, to: "parent" })`. `title` names it in plain words ("Pairing states"); `ask` is the line a reader of the canvas needs: what to judge and what to pin ("Judge the six pairing states: pin anything that reads wrong"). A surface of several screens is `file: [..]`, one states file per screen, each its own section, loaded as it comes into view. Add `edges` and `group` when the frames read better as a graph; add `dials` for what the person will want to tune (step 8): each sets a `cssVar` on the drawing or an `arg`; an `action` dial's arg counts his presses, so a story replays on it; a dial's `group` is the heading it stands under. Done when it answers an id.
5. **Read what was drawn.** The answer's `render` lists every frame: `drawn`, `empty`, `failed` (with its `file:line:column`) or `unseen`. Fix each `failed` and `empty` frame in the component or the story and read again (`artifact_read`, `render: true` to draw it now in the machine's browser). For each forced state, read its delta: `artifact_read({ id, state: { story, interaction: "hover" } })` answers which properties change on which element; an empty delta on a column that exists is a **finding**. A changed property is not yet the proof: the proof of a hover, a press, a selection or a focus is that the fill it paints takes its container's **contour**. In a rounded control it is that control's radius less its inset; in a bar's glass, the capsule's radius less its pad on the corners facing the glass's ends and the small join on those facing a neighbour. Read it from the delta: the fill's `border-radius` and box against its container's. Done when every frame is `drawn`, every delta says what you meant, every forced fill takes its container's contour, and `moves` lists the animations each flow fires (`references/proof.md`).
6. **Check it reads**, from the answer's `render` (labels, `unnamed`, `widthOnly`, `codeNamed`, `alike`, sections, frames per section): the ask names what to judge ("Judge the six pairing states: pin anything that reads wrong"); every frame is named in plain words by its doc comment, its form (`phone 390`) from `parameters.viewport`; the frames are grouped as the person thinks of them, a `title` section per screen with one states file each, flows and `edges` as the Map face's arrows, `group` as its regions; every state is one press away in the panel's design graph, its States list in the file's order. Fix the file or the call (`artifact_update` with `ask`, `edges`, `group`) until all four hold. Done when `unnamed`, `widthOnly`, `codeNamed` and `alike` are empty and all four hold.
7. **Show it** through the `show` skill. With nothing to choose, a component or a whole surface reaches the person as a preview at its path (`kind: "preview"`, `to: "parent"`), and your report says in one line what changed and what to look at. With a choice, ask it with the `decision-page` skill: one card per question, each option a `Preview` of your stories. Read their pins with `comment_read`: each carries the frame's `state` (story, interaction, scheme, width) and the element's `file:line:column`; change that line and answer in the pin's thread.
8. **Take their tuning back into the code.** He turns your dials and retimes your moves in the panel's design graph, its Dials and Animation faces. `artifact_read` answers `dials` (his value of each dial, by name) and `tuned` (each animation he retimed, `references/moves.md`). Write each into the component: a tuned transition's timing into its CSS or its motion call, a dial's value into a token or an arg default. A value that is no token yet goes into the project's token source first, then the component uses the token. Values he set answer the judgement and reach you by themselves, no Send; after a compaction `open_items` lists each canvas or preview you put to him, open or answered. Once the code carries them, close it: `question_close({ question: <its link>, as: "taken", why: <what he set> })`. Done when the code carries every accepted value, the canvas, read again, draws it, and `open_items` lists it no more.

## Before you finish

**Rehearse.** Draw at the width it is shown at and at 390, and at 2529 where the person will see it. Read every frame as a picture (`artifact_read` with `png` and `width`) and fix the largest fault first: framing (cut off, scaled, a plate or air nobody asked for), then hierarchy (where the eye lands first), then motion, then polish. Re-draw, and hand up once a full read finds nothing. The stage draws the picture; no browser of your own is opened for it.

**The fresh eye.** A reviewer sees only the frames and the URL, never your plan or reasons, and a finding quotes its frame.

**The report** names what you drew (widths, looks, states) and what you did not check.

| Check | Fails when |
| --- | --- |
| Reused, not redrawn | A frame draws markup a mapped component already renders, and that component is not in the frame's `parts` |
| Every state drawn | Any frame is `failed`, `empty` or `unseen` |
| Every state named | `unnamed` lists a story |
| One state, one story | `widthOnly` lists stories that differ only by their width |
| Each state looks its own | `alike` lists stories that draw the same picture at one width |
| Labels in his words | `codeNamed` lists a label with a word of code; or a label names a width, lists fields, or is a sentence he would not say |
| Only states that help him judge | A state he would not tell from another, or one no situation of his reaches |
| The ask says what to judge | It names no act, or names a file or a state code |
| Grouped as they think | One flat row where the person thinks in screens: use `title` sections, `edges`, `group` |
| A state takes its contour | A hover, focus, pressed or selected fill leaves its container's contour, or its delta is empty or names an element you did not mean |
| Moves move | A flow's `moves` entry lists no animations, or has an `error` |
| Tuning landed | `dials` or `tuned` holds a value the code does not carry |
| A choice asked on a decision page | The person must pick and the canvas alone is in front of them |
| The person sees a surface | The canvas's grid is what the person was given; a surface reaches them as a preview at its path |
| Weight | A component's states file is `over` budget (250 modules, 1 MB): its `cut` names the heaviest imports and whose each is. The states file's own imports are yours to cut; the component's own are its weight on any stage, and the story cannot cut them. A screen carries its weight |
