# Screen

A **screen** is designed from the journey in, never from the pixels out. The project's **DESIGN.md** is law: its tokens, named rules and component recipes decide every colour, size, radius, shadow, curve and duration. Find them in the project folder's `design/` (Caw: `folder_read`) or the repository's own DESIGN.md and token file. A value the design needs that no token holds is a token to propose, never a literal in the screen. The `show` skill's step 1 comes first: the screen reaches the person on the design graph with `does: "judge"` and an ask; its directions, when it has several, open in that one graph.

## Where the screen runs

Every screen is real code from the first one. Where it is drawn (the design graph on a Vite, Astro or Nuxt stage, a `page` artifact on any other stack, or a scaffold first when there is no code yet) is the `design-explore` skill's "Where the graph runs": follow it before step 1.

## Steps

1. **Write the journey**: who arrives, from where, what they came to do, the one action that finishes it, and where they go next. Read the product's own journey and voice rules when it has them (JOURNEY.md, DESIGN.md's Voice section). Done when the journey fits in five lines and names the screen's one primary action.
2. **List every state** the screen can be in: first use and empty, loading, filled, long and overflowing content, error, offline or refused, success. Colour schemes, widths and reduced motion are the graph's View: each state is drawn in all of them. Done when each state has one line on what the person sees and can do there, and which press or which situation outside their hands brings it. In a task, each state becomes a to-do (`todo_write` with `add`).
3. **Choose the parts**: the components the design system already has, by their recipe names. A part it lacks is described as a new recipe on the system's tokens. Done when every element of every state maps to a recipe or a proposed one.
4. **Build it where it can be seen.** The screen is a real component in the repository (`<Screen>.svelte`, `.tsx`, `.vue`) composed of the system's components. Read `design_map` first and mount the parts it lists; the `design-graph` skill is the loop, and its rule holds here: the mock stands at the screen's data, and everything on it is drawn by a real component.
   - **What the person opens** is the screen's live story: `<Screen>.stories.ts` in CSF 3, its one story mounting the screen once in the app's shell (its sidebar, its head, its panels, from the map) with mock data, its presses answered by that mock, opened with `artifact_create({ kind: "component", name, title, does: "judge", ask, file })` on the design graph, so they reach each state from step 2 by using it and switches width and scheme himself. The story's `component` is a fixture beside it that stands in for the app's root: it seeds the stores the shell and the screen read with product-shaped records through the stores' own writers, gives the contexts the app's shell gives (its sidebar's, its overlays'), answers the server's reads with the project's stand-in (the `design-graph` skill's mock table), and lays out the shell's rail and main as the shell does, so the screen's breakpoints answer at each of the graph's widths. One piece of the screen (a card, a row) is judged on a graph of its own, by the `design-graph` skill.
   - **Your reading** is a second states file, `<Screen>States.stories.ts`: one story per state from step 2 with fixture data as `args` and a doc comment each, in the project's real CSS, its parts' hover and focus included. Open it as a graph of its own with `reading: true`, which keeps it in your own panel for `artifact_read` until your work item ends.
   - **A flow they run through the whole running app** is a preview: `artifact_create({ kind: "preview", name, title, does: "try", ask, port, path, serve: { command, cwd } })`; CawCo runs that server in your workspace and keeps it up while the preview lasts, so don't start it in your own shell, where it ends with that shell.

   A toolchain the stage cannot run takes the `page` artifact ("Where the screen runs"). Two or more directions of the screen are one live states file each in the same graph (`directions`), the pick made there with its Pick and read as `artifact_read`'s `picked`; a choice that is no design goes on a decision page (the `decision-page` skill). Done when every state from step 2 is a story whose frame the graph reports `drawn`, and the live story they open answers each press with that mock data at each of the graph's widths.
5. **Check it against DESIGN.md**: every value a token, contrast at the system's floor, nothing outside its rules. The `drift` skill's search finds literals. Done when the check finds nothing, or each finding is fixed.
6. **End your turn**, then read their picks and pins with `artifact_read` and `comment_read` and revise in place. The design is done when they pick. It already stands on the product's real components, changed in place in your workspace; what the build still owes is the live data behind each mock, and your report names each one.
