# Gates: F1 — THE CUTOVER (destructive; operator-timed)

Scope: no repo code (docs/status log only). One event, obelisk first, then mac. Read the F1
warnings in PLAN.md before starting. Sequence: commit+push everything to main → verify
origin/main == local main → `cawco deploy init` on obelisk → stop old dev-tree units
(disable, keep .bak) → start clone units (sessiond, hub, dashboard, agent) → watch register,
bounded restore, board truth → repeat on mac (old-style update first to receive the new CLI,
then deploy init). The fleet is two machines: obelisk and the MacBook.

## Runbook, checked against the code (parent, pre-flight)

`deployInit` (service.ts:1329) does, in order: refuse a non-clone directory that already
exists -> clone (or fetch + `merge --ff-only` if already marked) -> **write the marker**
(0600) -> `bun install` -> build -> install units.

The marker therefore exists BEFORE any service starts, which looks like the ordering
hazard — it is not, and here is why: `checkDeploy` reads the marker **at its own checkout
root**. The marker is written into `~/.cawco/app`; the currently running agent lives in
the dev tree, which has no marker, so it cannot act on it. (It also predates C1 entirely
and has no poller at all.) Only an agent running FROM the clone can see it.

And when that agent starts, D4's unit carries `Wants=`/`After=cawco-sessiond.service`,
so sessiond is up first and every child the new agent spawns — including `restore`'s —
goes through D2's unconditional sessiond bridge. Custody is established from the first
spawn, before the poller can ever fire an update. The hazard is handled by unit ordering,
not by hoping about sequence.

Sequence to run:
  1. verify origin/main == local main            (G1 — satisfied: 29ac7f9)
  2. cawco deploy init                         (clone, marker, install, build, units)
  3. stop + disable the dev-tree units, keep .bak
  4. start: sessiond -> hub -> dashboard -> agent
  5. G2: claude children's ppid is sessiond's
  6. G3: restart the agent, child count must not drop   <- the tmux property
  7. G4/G5: units run from the clone, DB in the data dir, board truth matches ps
  8. then the Mac: old-style update first (to receive the new CLI), then deploy init
  9. G6: land a trivial commit on main, push, watch the fleet update

## ⚠ ORDERING HAZARD, raised by leaf C1 — read before touching anything

`deployUpdate` passes `restartAgent: true`. **Post-cutover that restart is free**, because
the children live in sessiond's cgroup and survive it — that is the whole point of the
build. **Pre-cutover it is not free**: on a machine where the agent still owns its children,
an auto-update restarts the agent and destroys every live session on it.

The poller is inert until the marker exists (`deploy.ts:201` returns `unmarked` before any
git command runs, and `~/.cawco` does not exist yet), so nothing can fire early by
accident. But it makes the cutover order load-bearing rather than cosmetic:

  **sessiond must be running and owning the children BEFORE `.cawco-deploy` exists.**

If the marker is written first and a push lands on main before sessiond has custody, the
first auto-update is the destructive one. Sequence sessiond → verify custody (G2) → only
then `deploy init`.

Also from C1: `deployUpdate` refuses any state but `behind`, and a diverged clone refuses
loudly rather than resetting — so a hand-edited clone will stop deploying and say so, which
is the intended failure.

## RESULT — obelisk cut over 2026-08-29 (parent, executed)

All six gates met on obelisk. Four defects were found by running it, all fixed and shipped;
none of them could have been found by reading, because each one only appears when the agent
and sessiond are separate processes with a restart between them.

### What the cutover found

**1. Every claude spawn through sessiond failed.** `Failed to spawn Claude Code process:
[sessiond] <id>: replay window lost, stream resumes at 1`, on all 14 restores. The wrapper
subscribes and only then asks for the child, so it always subscribed to a proc sessiond had
never heard of — and that branch answered with a reset AND returned before registering the
cursor. `#emit` fans out only to conns carrying a cursor, so even with the error suppressed
the child's output would have reached nobody. Fixed both ends (4e69c2e): a caller that has
consumed nothing gets an empty backlog with its cursor registered; a caller resuming from a
cursor sessiond never minted still gets §6's honest refusal, and only a reset that jumps past
the next expected sequence is fatal.

**2. The agent killed its sessions on the way out.** `shutdown()` stopped every session, and
`stop()` ends the child's stdin — a claude that loses stdin exits. The children live in
sessiond's cgroup precisely so a restart is free, and the deploy path restarts the agent on
every push to main, so this spent that property in exactly the case it was written for. Now
it detaches (9edd6a1); the log line is `detaching N session(s)`, not `draining`.

**3. A survivor the hub never named was left running with nobody pumping it.** The reattach
only saw sessions the hub asked to restore, and the hub restores from its own rows — so a
session it had written off (nothing to resume) stayed alive in `ps` while the board said
`error`. The agent now reads sessiond's own list and merges it (8eeb4a8). That needed a
directory per child, so `SessiondProcInfo` carries the spec's `cwd`.

**4. The database migration silently did nothing.** `LEGACY_DB_PATH` resolves relative to the
hub's own module, so from the clone it looked for `~/.cawco/app/packages/hub/cawco.db`.
The hub came up on a fresh 217088-byte database beside the real 8757248-byte one. Repaired by
hand during the cutover; fixed properly at 6966eec — `deploy init` does the move, because it
is the only moment that knows both ends.

### Two things an operator has to know

**sessiond is deliberately outside the deploy's restart set** (`type Service = 'hub' |
'dashboard' | 'agent'`, update.ts). That is correct — it is the process that must survive a
deploy — but it means a change to sessiond's own code is live only after a deliberate
`systemctl --user restart cawco-sessiond.service`, and that restart costs its children.
Do it when the board is quiet.

**The deploy leaves a busy agent running.** `restartAgent` skips when the agent is carrying
turns, so a push that changes agent code may not take effect until the machine is idle or the
agent is restarted by hand. The pull still happens immediately.

**The dev tree's `packages/hub/cawco.db` is still on disk** (8.7MB, now stale). It is the
file the live database was copied from. Left in place rather than deleted; if a hub is ever
started from the dev tree it would open that stale copy and diverge.

## RESULT — the MacBook, 2026-08-29 (parent, executed)

The fleet is two machines. "box" was never one: its row was last seen 2026-08-17 and its only
two instances were fixtures (`delegate-1`, `plain-1`, cwd `/home/o/cawco`). Row and
instances deleted; the hub now lists exactly obelisk and the MacBook.

**The Mac could not be updated remotely, and that was the whole blocker.** Its agent had been
running since 2026-08-08 and predated every verb the update needs — `updateCawco`,
`agentBusy` and `readMemoryFile` all answered `unknown session function`. There was no path
to it through the hub at all. `~/cawco` also turned out not to be a git checkout: it had
been copied onto the machine, never cloned, which is why it could never pull.

Rebuilt over SSH instead: old LaunchAgent unloaded, `~/cawco` deleted, cloned fresh from
origin, `bun install`, `cawco deploy init`. Note that `deploy init` installs ALL four
services — the Mac got a hub and a dashboard it must not run, and both were removed with
`cawco service uninstall hub dashboard`. It now runs sessiond and agent only, and finds
obelisk by config (`~/.config/cawco/config.json`, which survives the rebuild).

    MAC G3  the tmux property      agent 73939 -> 75060, sessiond 73936 unchanged,
                                   claude child 74798 identical across the restart
            and it was adopted     "detaching 1 session(s)" -> "took custody of 1"
    memory  peek/busy now answer   both were `unknown session function` for three weeks

**The memory conflict is resolved by overwrite** (operator's call). The Mac's own version was
recorded to fleet history first — entry 13, 1872 bytes, source `machine:271a214a5d568e4c` —
so the edit nobody had seen is recoverable through `/api/fleet/memory/restore`. After the
push both sides hash `f15663451e8f0f90` at 3153 bytes with 2 docs.

One cosmetic leftover: a few claude SDK processes on the Mac still run from the deleted
`~/cawco` path, parented outside cawco. They are not the fleet's and were left alone;
they will go when whatever owns them exits.
