# Projects in CawCo — decisions and spec

Owner session 2026-10-06. This file is the record; every change to the plan below is appended to the decision log at
the bottom with the owner's words.

The decisions were made on a decision page: https://claude.ai/artifact/JBzcHeuFzFgSGyv5RLRzSX (21 decision cards, each
with an animated mockup, the owner's picks and notes). Its source and mockups are in `mocks/project-paths/`
(`python3 mocks/project-paths/build.py` rebuilds it). The mockups illustrate behaviour; DESIGN.md decides every pixel.

## 1. Why

Today a project is one folder on one machine. The same repo on two machines is two projects, knowledge work (a launch,
an X account, SEO) has nowhere to live, delegates are tracked but "done" never meant "on main", and the supervisor,
autopilot and assistant panel are a small model's one-shot verdict with no tools, memory or board.

Goal: a project is one identity across machines and kinds of work (code, knowledge, design). You talk to it through
Caw; work that must outlive a chat becomes tasks; code runs the tasks, checks and landing; models judge; you decide.

Not in scope: two-way tracker sync, an adapter per design tool, a design editor, a memory service or vector index, a
resident fleet watcher, any chat-app bridge.

## 2. Standing rules (owner)

- **Talk first.** Every primitive is optional and reachable by talking; none sits between you and a session. A session
  never needs a task. Tasks appear when work must outlive a chat or run without you (delegated, async, routine,
  multi-day), and Caw files them from what you said. (steipete's "just talk to it", §11.)
- **Caw suggests, you escalate.** When a plain session outgrows itself (runs for days, spawns delegates, leaves
  follow-ups, needs a schedule, touches several areas), Caw offers "make this a project" once. Accepting creates the
  project from the session: its checkout as a place, its open plan items as proposed tasks. Never automatic.
- **Derived liveness.** Running, checking, landing, stuck and needs-you are read from processes and sessions, never
  stored, never written by a model, never a stage.
- **Code coordinates, models judge, you decide.** Status, frontier, caps, checks, landing, schedules and approved
  actions are code. Judgments (is this ready, which type, does this meet the criterion) are models. Permissions,
  merges, config writes and public actions are yours.
- **Files are the truth.** Tasks, stages, delegate types, routines, skills, views, decision pages and memory are files
  in the project folder. The hub keeps indexes rebuilt from them and the live state.
- **Jev on → Jev. Jev off → the model already in the loop → the rule.** Off: the lead, or the session that is asking,
  decides with its own model, never about its own work; questions with no session behind them wait for the lead's next
  wake and go as one batch. Answers keep Jev's shape (yes/no, choice, score) and the feature says who decided. Jev on
  but failing says so and does not hand the question to a session. Jev never writes status or answers a permission.
  This supersedes the 2026-09-23 rule for the not-connected case only (decision log).
- **One word per concept** (WORDS.md). New and changed terms are in §3; they land in WORDS.md before any UI.
- **DESIGN.md is law** for every surface here: tokens from `design/tokens/cawco.tokens.json`, its rules and recipes.
- **No adapter per outside tool.** If a tool has an MCP server, a session uses it and CawCo shows what it saved.
- **Public actions wait for you by default.** A project can loosen that per stage move, explicitly; never by default.
- **The phone path is the iOS app.** Its push and the transcript are how the hub reaches you; there is no other bridge.
- **Work outlives its surface.** Work a window, sheet, tray, popover or dialog starts survives a reload with that
  surface open at the same step; dismissing it parks the work in one persistent place with live progress, one press
  brings it back, and every failure says its cause and a way to recover (DESIGN.md, The Work Outlives Its Surface Rule).

## 5. Spec

### 5.1 Project shape (D1, D15, D16)

- `projects` loses `machineId, cwd` and gains `remote?`, `places[]` (checkouts on any machine, delegate workspaces) and
  a hub-kept, git-versioned folder. Existing rows migrate as one place each.
- **A project runs on any machine.** A project with no outside remote gets the hub as its remote: a bare git repository
  per project, served over the tailnet by git's own HTTP backend behind session and machine credentials. Running it on a
  machine without a checkout clones from the hub there (a new checkout place). Machines reconcile through git: each pushes
  its work to its own branch and the merge queue lands it (§5.3); a conflict is a Needs-you card. Moving work in progress
  snapshots the source's uncommitted changes to `cawco/move/<machine>`, which the target checks out. Secrets and ignored
  files never move; the session installs dependencies on the target as it needs them (CawCo installs none). Large files go through Git LFS: the hub is the LFS server for
  its remotes (the Batch API at `<remote>.git/info/lfs/objects/batch`, the `basic` transfer adapter, objects stored on
  the hub by sha256), so a clone fetches pointers first and the large files as their own stage. When CawCo first makes
  a repository of a plain folder (D28's first commit), files over GitHub's 50 MiB warning size stay out of that commit,
  are named in the thread's note, and the note carries a card offering Git LFS for them by pattern (a row per `*.<ext>`
  with its count and size; Track with LFS runs `git lfs track <patterns>` and a second commit, git-lfs-migrate(1)'s
  no-rewrite path; Not now leaves them out). A project whose outside remote has LFS keeps using that remote's LFS. A
  project may instead declare where its large files live (Project details › Large files: an LFS URL bound to a fleet
  connection for that host). Every git-lfs run on a machine for a project is pinned to one endpoint, the declared one or
  its origin's own, and one credential, whatever the repository's committed `.lfsconfig` says; a `.lfsconfig` naming any
  other endpoint leaves its files as pointers, and the thread is told which endpoint it asked for and how to declare it.
  A folder that is not a git repository becomes one with no card (D28, decision log 2026-10-14). Before a session starts on the new machine, its setup is a visible wait with real stages
  (cloning, ready) and ends by naming what moved and what stayed.
- The project folder:
  ```
  AGENTS.md      you own it; agents propose
  tasks/         one file per task (§5.2)
  stages.md      stages, kinds, moves, views (§5.2)
  gate.md        the merge checks: the steps the hub runs before work lands
  views/         saved and agent-built views
  delegates/     delegate types, one file each
  routines/      one prompt file each
  skills/        project skills and MCP servers
  knowledge/     brand kit; facts as dated, sourced lines (Formerly, Conflict); archive/
  memory/        curated + agent inbox
  assets/        images, designs, versioned by hash
  design/        DESIGN.md, tokens.json, components.json, references/, explorations/ (design projects)
  decisions/     decision pages (§5.8)
  ```
- Project skills and MCP servers reach every place of the project: each checkout, each delegate workspace, the hub
  folder. Pinned by commit when installed from GitHub.
- Delegate types are files in `delegates/` and shadow fleet types of the same name:
  ```
  ---
  harness: claude
  model: claude-opus-5-5
  effort: high
  skills: [brand-voice, x-post]
  mcp: [x-brand]          # named connections (§5.5)
  role: web-facing        # its toolset (§5.3)
  budget: { usd: 2, per: day }
  lands: none             # drafts, not commits
  ---
  Draft posts in the brand voice.
  ```
  A type is a preset: no persona text. Which type runs a task: the task names one → that type; else the dispatcher asks
  (Jev, or the lead's model) for a choice over the project's types; else "medium". The catalog a session sees is fixed
  at its start (the `delegate` tool description feeds the prompt cache). A type runs only on a machine where its harness
  and model are installed and signed in. Caw can propose a new type as a file diff you approve.

### 5.2 Tasks, stages, views (D2, D12, D17)

- **Tracker per project:** CawCo files (default), GitHub Issues or Linear. One record, never two-way. With GitHub, the
  tracker owns issue fields; CawCo owns rank, edges, attempts and checks. Projects v2 webhooks exist only for org
  projects, so user projects are polled.
- **Task file** (`tasks/<id>-<slug>.md`), sections borrowed from Backlog.md, edges from beads:
  ```
  ---
  stage: draft
  type: writer                 # assigned delegate type
  after: [138]                 # blocks
  parent: 120                  # parent-child
  related: [131]               # no effect on ready
  found_in: 140                # discovered-from, audit only
  checks: ["bun test", "bun run lint"]
  outputs: [post.md]
  rank: a0V
  labels: [ui]
  ---
  Description.
  ## Acceptance criteria
  ## To-dos
  - [x] Token for the toggle
  - [ ] Persist the choice
    - [ ] Read the stored value on load
  ```
  Agents write through `task_*` MCP tools; a hand edit is picked up by hash; git keeps history. Import from Backlog.md
  and beads.
- **To-dos** nest as indented checkboxes. A to-do that grows is promoted to a task with an edge; its line becomes
  `- [ ] → #152` and ticks when that task lands. Triage, edges and the dispatcher only ever see tasks.
- **Plan ↔ to-dos, no drift:** the plan is CawCo's list (`todo_write`'s session scope); to-dos are CawCo's too
  (`todo_write`, own task only). The brief asks the session to start its plan from the task's open to-dos with their
  ids (`[td-3] Persist the choice`); a plan item carrying an id ticks that to-do when it completes; `finish_item` lists
  unticked to-dos and the session ticks or explains each; plan items left open become proposed to-dos.
- **The plan model** (owner, 2026-10-20, "Yes, build it" on "Is this the plan model you mean?"). Seven points, each
  with why; hub `plans.ts` keeps the plan, `plan-changes.ts` decides who hears a change and when:
  1. **One plan per session, in CawCo's list on every harness.** Why: two lists drift, and the person's changes need
     one place to land. Every session is denied its harness's own list and plan mode at spawn, beside the fleet's
     denied-tools baseline and never stored in it (core `OWN_LIST_DENIED`), and the machine's own `claude` settings
     carry the same: Claude Code's `TaskCreate`, `TaskUpdate`, `TaskList`, `TaskGet`, `TodoWrite` (agent SDK 0.3.302's
     `BUILTIN_TOOL_NAMES`) and `EnterPlanMode`/`ExitPlanMode`; OpenCode 2.0 has no list ("The `todowrite` tool is no
     longer available and must not be called", 2.0.29) and its `plan` agent is off in every server CawCo launches; pi
     has neither. It is no choice: not in onboarding, Settings or a delegate type.
  2. **A working session hears every change at its next step**, without being stopped: reword, add, remove, comment,
     tick, move. Why: it is mid-work on that plan, and the one send path already folds a person's words into a
     running turn at the next tool boundary (`PLAN_ORIGIN`, a person's act).
  3. **An idle session is started by a change to the work**: a reword, add, removal or comment starts it 3 s after the
     person's last such change, every change of that window in one message. A tick or a move starts nothing; it goes
     ahead of its next turn, whoever starts it, and in its next `todo_write` answer. Why: a changed step is new work, a
     ticked or moved one is bookkeeping, and the quiet window keeps a burst of edits to one wake.
  4. **An ended session is reopened by the change** (finished, archived, a delegate whose item is done), the same send
     reopening it as the person's words do. One that cannot go on, its conversation or workspace gone, is followed by a
     new session in the same project and place, opening on the change, the old session's plan and its records (its
     open items: plan, spec, task to-dos, decisions, notes). Why: the plan stays with the work, and the records are what
     the hub still holds when the transcript is what went.
  5. **A delegate's plan answers to the session that delegated it.** A change to any step of the main plan goes to the
     main session, never straight to the delegate; a change to the delegate's own plan goes to its parent too. Why: the
     main session owns the plan and decides what reaches the delegate.
  6. **A task attempt's plan answers to Caw**, the project's lead, who dispatched it: he decides whether to tell the
     running attempt, start a new one, or reshape the task. Why: the task is his to steer.
  7. **A step waiting on the person's choice links to its card** on a decision page (`todo_write`'s `waitsOn`: the page's
     artifact id and the card's id, set by the session as it asks), and the plan shows it "Waiting on you". The page's
     Send with a pick for that card wakes the session as before, and the step stops waiting. The hub sets a wait on the
     whole artifact itself (`waitsOn` with no card) on the session's current step when its `artifact_create` or
     `artifact_update` with `does: pick` or `judge` returns; it stops waiting once nothing on the artifact waits on the
     person, and while it waits the artifact stays in Needs you (§5.2, Needs you). Why: the person sees what waits on
     them where the plan is, and answers in the page that asked.

  The person's words go into every message verbatim, step by step ("Reworded “old” to: “new”"), with the plan as it
  now stands. A session's write of its steps that would undo a change it has not written over since (a reworded step in
  other words, an added one gone, a removed one back, a tick turned) is refused once, naming each; a step keeps the
  person's comments and its wait across the session's writes, by id. The person changes a plan through
  `POST /api/instances/:id/plan/edits`, the owner's alone: no agent's edit comes that way, and none wakes anyone.
- **Every session's plan, in a panel.** A session never needs a task (§2), so the plan reaches a plain session too:
  `todo_write` gains a session scope beside its attempt scope, holding the session's steps in Agent Client
  Protocol's plan shape, nested by indent. The session's spec (`todo_write`'s `spec`, the document its denied plan
  mode would have written) is shown read-only beside it. The plan's ring, on the composer's tray row, opens it as a
  floating layer that rises from the row over the transcript's foot, across the composer's width, at every width
  (DESIGN.md, The Composer Layer Rule): it moves nothing, the transcript included. It shows the session's plan live;
  on a task attempt it also shows the task's to-dos, ticking, and links to the project's canvas view for the task's
  edges. Edges stay on tasks: a step that needs
  an edge is promoted to a task. Updates ride the ledger as AG-UI-named state and activity events.
- **Stages** (`stages.md`): each project names its stages; each stage has one kind:

  | Kind | Means to CawCo |
  |---|---|
  | todo | the dispatcher picks it up |
  | active | entering can start a delegate type (`runs:`) |
  | waiting | a routine or poller moves it on (`until:`, `after:`) |
  | you | it lands in Needs you and on the phone |
  | done | counts as finished in recaps |
  | dropped | closed, not counted |

  `moves:` lists allowed moves and who may make them (`you`, `action`, `lead`, `routine`). Templates: code
  (ready → working → review → done), social (idea → draft → review → scheduled → posted → measured), outreach
  (prospect → contacted → replied → meeting → won | lost), SEO, design (brief → explore → review → picked → build →
  shipped). With GitHub, stages map onto a Projects single-select field. The task file's `status:` is `stage:`.
- **Needs you** is a lane, not a stage: every card of kind `you`, every session that is asking, and every artifact waiting on the person.
  An artifact waits on the person (core `artifact-needs.ts`, one item per artifact, its reasons strongest first): shown
  and never opened, for `does: pick` or `judge` ("New · not opened"); a decision page's picks not made ("3 of 9
  picked"); picks, notes, pins or ink written and not sent ("2 unsent"); an agent's answer on an open pin newer than the
  person's look ("1 new answer on pin 12", §5.7). Never a `try` preview, a `draw` canvas with nothing pinned, or one
  the person can't act on yet (handed up to a parent that hasn't opened it); picks sent and not yet read are the
  session's move and ask nothing more, while what is still unpicked stays the person's. The hub derives it from the doc and the person's own marks on every read, never a
  stored flag, and serves it with the lane (`GET /api/artifact-needs`, the `artifact.needs` frame, and `/api/pending`,
  where one envelope carries that frame). It leaves by rule: answered (a partial answer leaves the rest); the writer
  moved on (the hub sets the writer's current step's `waitsOn` when `artifact_create` or `artifact_update` with `does:
  pick|judge` returns; the ask leaves once that step is ticked or removed, or, with no step waiting, once the writer's
  next turn ends with no new show of it); superseded (a revision or a same-name create changes the row in place); its
  session ended (it leaves for one notice, "<harness> ended; 3 picks on <name> never made"); Not now (the person's ✕,
  until it is raised again by a revision or a new answer); a look (opening clears "not opened" and the notices; only an
  answer clears picks or unsent). A revision with nothing asked ("4 changed since you looked") and a resolved pin's
  unread closing answer are notices, never needs.
- **Views** are settings over the same tasks: board (Pragmatic drag and drop, in the dashboard), table (TanStack
  Table), calendar (Event Calendar, MIT, Svelte 5), pipeline, canvas (Svelte Flow, in the dashboard), and any view
  Caw designs: "Ask Caw for a view" (optional) adds a custom view as its own tab beside these.
- **Pages are blocks.** A page's tab content (the routines tab, a task view's surroundings) is a stack of blocks in one
  frame (title, optional count, a menu to move or hide): the built-in ones plus any custom view placed as a block. One
  custom view, two places: the same view shows as its own tab or as a block on a page, and its menu moves it between
  them. You arrange blocks: each block's order and
  width (narrow or wide) is yours, saved per project for every device, and the grid reflows it to the screen (four
  columns wide, two on a narrow desk, one on a tablet or phone; every block keeps a readable measure). Drag a block by
  its frame on the desk (Pragmatic drag and drop, as the board), long-press or Move up/down on a phone. A custom view is
  written in OpenUI Lang (openui.com, MIT) over CawCo's component library, bound to data the hub computes
  through the library's `Query`/`Mutation` tools, which are hub routes only; it is stored as `views/<name>.oui`. The
  dashboard renders it with CawCo's Svelte binding over `@openuidev/lang-core`'s runtime (its parser, store, query
  manager and evaluator, as react-lang's Renderer binds them; `@openuidev/svelte-lang` 0.4.1's Renderer runs no Query
  tools) and our components (DESIGN.md; OpenUI's own component library and theme are not loaded); the prompt comes
  from `@openuidev/lang-core`'s `generateSystemPrompt` over our library spec, generated at build time. The app shows the same block in a web view running the dashboard's renderer, since
  OpenUI has no Swift renderer and a hand-written one is not ours to maintain. Kept only when you approve; a view
  cannot run code or reach the network (OpenUI: "The model only composes your components and never runs arbitrary
  code"; its tools are ours); a component outside the library is dropped and reported, not invented.
- **Progress** is derived: to-dos ticked per task, tasks landed along edges per spec. Ticking every to-do never makes a
  task done; checks and landing do.
- **Shapes we borrow, not engines:** plan entries in Agent Client Protocol's shape (pending, in_progress, completed);
  an attempt's live state named after A2A / MCP Tasks (working, input-required = needs you, completed, failed,
  cancelled), so outside agents can hand CawCo a task; ledger events named after AG-UI's state and activity events.
- **Visibility for agents:** every brief says where its task sits (spec, what landed upstream, what waits on it).

### 5.3 Running work (D3, D4, D5, D6, D7)

- **Caw, the project lead:** a session on Claude Code, OpenCode or pi with board tools, the fleet's MCP servers, and shell

  result, a fleet nudge). On or off per project: default on for projects made with Caw, off for migrated ones; each
  lead shows its spend. Off: you write briefs and nothing wakes a model. The hub decides each shell or edit call

  workspaces with checks and landing (his edits are docs, config and assets, 5 files a wake; 20 calls a wake; in a
  shared checkout `git checkout|switch|restore|reset|stash|clean|rebase|push`, any git alias, and `git add -A|.` are refused: file a task); and his
  long context keeps his turns costly, so real work is delegated. A turn your message woke runs read-only commands
  and, where no one else works, `git init`, `git add <paths>` and `git commit` without asking; any other call raises
  the Approve card. A turn anything else woke (an event, a routine, a report, outside text on his wake), and every
  call after he read web content in a turn, raises the card for every call. Every call is a note in his thread.

  lines (a delegate's disposable clone keeps them). The protected config it has (`.mcp.json`, `.claude/settings.json`,
  `.vscode`, `.git/config`, shell rc files…) is bound read-only where it stands; what is absent is refused to his file
  tools by name, and after each command his place's guard moves to scratch, never deletes, anything protected the command
  made, renamed or linked in, or a link to protected config outside, failing the command with a note; a protected file

- **Fleet watch** replaces the supervisor, autopilot and assistant panel: code detectors with two sources; Jev asks
  stuck / looping / off-task on fresh transcript slices and only a yes wakes a fresh Caw triage run (one decision,

- **Delegate upgrades** (all nine): hub-owned landing with a per-repo merge queue (verified push, rebase, re-run checks,


### 5.4 Knowledge and skills (D8, D14)

- **Memory:** you own AGENTS.md and the curated tier; agents write to an inbox; a curator run proposes, you tap.
  "Make a note" from you writes straight to AGENTS.md as a diff, and the notes gather in one standing notes thread per
  project: the first note opens it, later notes join it. Routine, heartbeat, subagent and web-tainted notes
  never become candidates. Files and grep; no vector index. Jev classifies inbox notes (lasting fact, scaffolding,
  secret, untrusted, duplicate); off: the curator decides on its next run, rules filter first. A note's words pass the
  secret filter (hub `secret-filter.ts`: secretlint's recommended preset, a password-shaped word in a sentence
  about a password, passphrase, keychain, keyring, unlock, login or sudo, and a credential set to a value:
  `password=…`, `token: …`, `Bearer …`) before it is committed: each secret is
  written `[redacted]` and the note is marked secret. No curator, fold, reshape or archive proposal touches AGENTS.md's
  `## Notes`, your own.
- **Facts are lines** (hub `memory-facts.ts`). A `knowledge/<topic>.md` file opens with a line saying what it holds,
  then one line per fact: `- <fact> (since <date>, from <note ids>, used <date>)`, with at most one indented
  `  Why: <grounding>` line under it. `since` is when the fact became true (the note's day, or the day the note
  states with `memory_note`'s `since`); the commit is when CawCo learned it. A line reading `(ruling <date>)` in place
  of `since` and `from` is your own word: only you write one (re-grounding a fact in a card's diff before approving
  it); a ruling never folds, never retires when a note is withdrawn and is never archived for disuse. `until` is a
  known end: once it has come, a curator run's start proposes the line under Formerly, no model asked. A changed fact
  keeps its old line under `## Formerly` as `- <old fact> (since <d1>, until <d2>, from …, replaced by <note id>)`,
  one Formerly line per fact: a second replacement moves the older to `knowledge/archive/` in the same card; a
  same-subject, same-property, same-period disagreement keeps both lines under
  `## Conflict`, never settled by a model (you edit the file or send a later note). A line that does not read is
  reported by its file and line, never guessed. Point in time needs no tool: `since`/`until` answer "true on a date",
  git answers "known on a date". A knowledge file written as prose before fact lines gets one card as a curator run
  starts that rewrites it word for word as fact lines, one per claim (`since` the day git blame dates the claim, the
  file's mtime where git has none; `from` `knowledge/<file> (before facts)`); until you approve it, a brief carries it
  as one block marked "not yet fact lines". Rejecting it declines that prose: the card comes back only once the file
  says something else.
- **Sorting a note against the facts:** for each lasting note, code greps `knowledge/` for the lines sharing its
  subject; Jev answers one choice per (note, line): corroborates (the note joins `from`), changes (old line to
  Formerly), conflicts (both to Conflict) or unrelated, in the same request as the inbox's sort. A clear answer
  (confidence 0.5 or more) pre-fills the proposal, one card per file; a spread one, a note no line relates to, and
  every note with Jev off go to the curator's run with the lines grep found.
- **Withdrawing a note** (yours, `POST /api/projects/:id/memory/notes/:note/withdraw`): one card moves every fact
  resting on it alone to `knowledge/archive/` and the note to the archive as withdrawn; a fact with other sources
  keeps them, a ruling rests on none and stays. Editing a line to `(ruling <date>)` in the card before approving keeps
  it as your word. A note no fact rests on is archived at once. Purging a session (deleting its transcript from the
  dashboard) withdraws every note it wrote the same way, and its machine's transcript index forgets its words, so
  neither Find nor an agent's `find` answers with it.
- **Fold, reshape, archive** ("fold first; archive a fact only after long disuse"): a file past its budget asks the
  curator's run for a fold, which shortens or drops `Why:` lines and never merges or rewords a fact line (a change
  citing no notes that does is refused); every curator run judges whether a file's facts fall under two descriptions
  and splits it, and more than 25 fact files ask for a reshape toward 15 to 25 (lines moved whole, never reworded;
  under 15 files a reshape never merges files); lines no brief carried and no note corroborated for the archive's
  days, rulings aside, are proposed moved to `knowledge/archive/` with their history. Each is a card you approve; rejecting an archive card keeps its lines as used now. `used` comes from the hub's record of what briefs carried (db
  `fact_uses`) and is written only inside a diff proposed anyway. The archive's days and a file's budget are hub
  config (`CAWCO_MEMORY_ARCHIVE_DAYS`, `CAWCO_MEMORY_FILE_CHARS`), their defaults measured by a replay
  (`scripts/probe-kit/specs/memory-replay.ts`).
- **Brief builder:** task, checks, last failure, where the task sits, AGENTS.md, and the fact lines the task needs,
  whole, with their dates and sources, within the brief's budget: grep's shortlist of the task's words (and every line
  of a file the task's `context:` names), ordered by Jev's yes/no per line on whether it bears on the task (off:
  grep's order); current lines before Formerly ones, a Conflict line with its other side, marked. A brand kit file
  the task names is carried whole.
- **Find** (`find`, read-only, every session that works): what any session, thread, task, routine, artifact,
  decision, commit or file said or holds, searched the way the person does in the dashboard's Find, through the same
  engine (hub `find.ts`): names at the hub, transcripts through each machine's own index. It narrows by project,
  machine, day (`since`, and `before`: evidence at or before that day, past.dev's `queryTimestamp`) and who said it,
  pages with a cursor, and reads a hit's neighbouring turns (`around`). A delegate in a project searches its own
  project unless it asks for all. Every text it answers an agent with passes the secret filter first, each excerpt
  cut from its whole turn after filtering (never from the index's snippet), so a password you typed into a chat
  comes back `[redacted]`; a session you purged is no hit (db `purged_sessions`, which also covers the time before
  its machine's index forgets it). The
  dashboard's Find, yours, is unfiltered. The hub keeps no prose of its own for it.
- **Skills:** our own, written with mattpocock's `writing-for-agents`: `grill` (interview to a spec), `to-tasks` (spec
  to tasks with edges and checks), `triage` (needs-info, ready-for-agent, ready-for-human, won't do); design skills
  `screen`, `restyle`, `drift`; each template's starter skills; `decision-page` (§5.8). Kept from Matt's skills: tasks
  end to end with blocking edges, acceptance criteria per task, interview before planning, triage states. Dropped:
  his tracker setup, scanning files for ready work, in-harness implementers (CawCo's board and dispatcher replace
  them). Skills are optional; a task can be one line with no spec.

### 5.5 Time, events, phone (D9, D10, D11)

- **Routines** live in hub SQLite on Effect 4's `Cron` (time zones). Each tick: one transaction inserts `run(routine,
  slot)` (fires once) and computes the next slot (misses collapse); overlap is skipped with a reason; else a fresh
  session in the routine's delegate type, or a message to the lead. Hub start: one catch-up, newest slot. Output
  contract: `NO_REPLY` (silent), `AUTOMATION_FAILED` (retry, then Needs you), anything else is the deliverable.
  Agent-created routines expire after 7 days unless kept; a new routine runs once at once as a test; budgets apply to
  routine runs.
- **Ingress:** pollers by default (GitHub every 60 s with an ETag; a 304 is free), plus a **connector poller** that
  polls any connection's read tool on a schedule and diffs results into `inbound_event` (unique on source + delivery
  id). A matcher in code (author, label, branch, regex) picks a routine; unmatched events go to the lead's next wake.
  Payloads reach models as data, never instructions.
- **Relay** (optional): one public path `/hooks/<id>` through Tailscale Funnel (or Cloudflare Tunnel) to a receiver on
  127.0.0.1 that is not the hub API: signature check (GitHub, Stripe, generic HMAC), timestamp window, 1 MB cap, rate
  limit, write-only. Setup is one action (Caw, Settings, `cawco relay on`): pick the host, approval card, `tailscale
  funnel --bg` for `/hooks/` only, create id and secret, register at the source by API where possible (else Caw guides
  pasting), test delivery, Caw proposes the matcher and routine as a diff. The hub stores the wanted state; daemons
  re-apply it on start; host offline → polling, and the connection says so. Caw's brief carries one line about inbound
  state; Caw offers the relay when you connect a push-only service. Proposed: a pull relay variant (§9).
- **Approved actions:** you approve one exact tool call (connection, account, arguments); the hub runs it once at its
  time through the connection (outbox, idempotency key). Never a model. Stage moves with `by: action` happen only this
  way.
- **Connections:** named rows with hub-held sign-in (OAuth or key); two accounts are two rows (`x-brand`,
  `x-founder`); a delegate type lists the ones it may use; keys never reach a session.
- **Phone:** content-free APNs push from the hub ("site needs you"), the app fetches details over the tailnet; then
  Caw's project threads in the app; then approvals in the app.

#### iOS app, to build on the desktop session

The hub side shipped in P2 (`packages/hub/src/push.ts`, Settings → Phone). This is the app's half, exact enough to
build without guessing. The hub never puts tool input, paths or prompts in a push; the app reads them over the tailnet.

**Capabilities.** `project.yml`: Push Notifications on the `CawCo` target (`aps-environment` entitlement:
`development` for Xcode builds, `production` for TestFlight and App Store), and the Background Modes key
`remote-notification` is **not** needed (alerts only, no silent pushes). Bundle id `dev.cawco.app`, which is the
default in Settings → Phone.

**Registration.**
1. On first connect to a hub (after Connect succeeds), `UNUserNotificationCenter.requestAuthorization([.alert,
   .sound, .badge])`. Granted → `UIApplication.shared.registerForRemoteNotifications()`. Denied → nothing; the
   app's own settings row says "Notifications are off in iOS Settings."
2. `application(_:didRegisterForRemoteNotificationsWithDeviceToken:)`: hex-encode the token lowercase
   (`token.map { String(format: "%02x", $0) }.joined()`), then POST it to every hub the app knows (today one). Do
   it on every launch: tokens change, and the hub upserts.
3. The route is hidden from `openapi.json`, so call it with `URLSession`, not the generated client:

   ```
   POST {hub}/api/push/register
   Content-Type: application/json
   {"token":"<hex, 64+ chars>","environment":"sandbox"|"production",
    "name":"<UIDevice.current.name>","platform":"ios"|"ipados"|"macos","quiet":<bool, optional>}
   → 200 {"ok":true,"quiet":<bool>}   400 text/plain when the token is not hex
   ```

   `environment` is `sandbox` when the build's `aps-environment` is `development` (compile-time `#if DEBUG` is the
   proxy the scripts already use), else `production`. `platform` is `macos` under Mac Catalyst, `ipados` on iPad,
   else `ios`. Omit `quiet` on launch so the hub keeps what the operator set; send it only from the toggle below.
4. **Quiet** toggle in the app's settings ("Quiet: registered, and sent nothing"): POST register again with
   `quiet` set. The answer's `quiet` is the truth to show. Settings → Phone on the dashboard flips the same flag.
5. **Sign out / forget hub:** `POST {hub}/api/push/unregister` with `{"token":"<hex>"}` →
   `{"ok":true,"removed":<bool>}`. A token APNs reports gone (410) is removed by the hub on its own.

**Payload.** Every push is an alert, `apns-push-type: alert`, priority 10, one day expiry:

```json
{"aps":{"alert":{"title":"<session, task or work item name>","subtitle":"<project name, when there is one>",
  "body":"Needs you"},"sound":"default","category":"<below>","thread-id":"<projectId or instanceId>"},
 "cawco":{"kind":"ask","instanceId":"…","machineId":"…","projectId":"…"|null,"requestId":"…"}}
```

`cawco` by `kind`: `ask` (above); `turn` `{instanceId, machineId, projectId|null}`; `artifact` `{artifactId, instanceId,
machineId, projectId|null}` (a turn that left an artifact waiting on the person); `task` `{projectId, taskId, instanceId|null, machineId|null}` (the newest
attempt's session, when the hub still holds it); `attempt` `{projectId, taskId, workItemId, instanceId,
machineId|null}`; `test` `{}`. `apns-collapse-id` is `ask-<requestId>`, `artifact-<artifactId>` (a revision's push
replaces the older) or `task-<projectId>:<taskId>` (a failed attempt and its task share one, so they replace each other).
Unknown `kind` or category: open the board.

The sealed alert (`e`) is `{"v":1,"title","subtitle"?,"body","options"?}`. `options`, `[{"id":"<index>","label"}]`,
is set only on a session's `AskUserQuestion` of one single-choice question with one to three options (push.ts
`inlineOptions`; a multi-select stays Open only, since one tap can't say several picks);
the labels are the agent's words, so they travel sealed, never in `aps`.

**Categories and actions.** Register the fixed ones at launch with `UNUserNotificationCenter.setNotificationCategories`
(CawCoPush `PushCategory.install`, which merges: the call replaces the whole set):

| Category | Sent when | Actions |
|---|---|---|
| `CAWCO_PERMISSION` | A session asks permission for a tool that is not a shell, a plan, a subagent or an MCP tool | **Approve** (`APPROVE`, `.authenticationRequired`), **Deny** (`DENY`, `.destructive` + `.authenticationRequired`), **Other…** (`DENY_WITH`, text input, `.authenticationRequired`: denies with the typed words as the denial's `message`), **Open** (`OPEN`, `.foreground`), in that order |
| `CAWCO_PERMISSION_OPEN` | Permission for `Bash`, `BashOutput`, `KillShell`, `ExitPlanMode`, `Task` or any `mcp__…` tool | **Open** only: these are read before they are granted |
| `CAWCO_QUESTION` | A session asks a question | **Open** only, unless it carries `options` (below) |
| `CAWCO_QUESTION.<hash>` | Set by the notification service extension on a question push whose sealed alert has `options` | One action per option (`ANSWER_<id>`, its label), then **Other…** (`ANSWER_OTHER`, text input); all `.authenticationRequired`, not foreground |
| `CAWCO_TURN` | A session the owner started (top level: not a delegate, lead or summariser) ended its turn with a result no rule answered; not a turn they stopped, nor one a restart cut (no result). Waits 5 s first and goes only if nothing marked the session looked at (`/api/seen` `look`: SessionSurface posts it for a session in front on a visible page as its turn ends, and the app's ShellController under the same rule for one in front with its scene active). Sealed body: the reply's first line. Collapse id `turn-<instanceId>`, sent past the hub's 10 s same-moment hold (that hold is for a task's move and its failed attempt, which share a collapse id), so a newer turn's push always goes and replaces the older. The same session failing to start or dying goes the same way at once ("Failed", the reason's first line sealed). Any session's `send_to_user` goes too, under `message-<instanceId>` ("Sent you a message", the message's first line sealed); its words and files are the call's row in the transcript. A look clears both | **Open**, **Reply** |
| `CAWCO_TASK` | A task entered a stage of kind `you` (moved by the hub, a session or the lead; never your own move) and a session has worked on it | **Open**, **Reply** (`REPLY`, text input, `.authenticationRequired`) |
| `CAWCO_TASK_OPEN` | The same, before any attempt; and the turn's push of a turn that left an artifact waiting on the person (§5.2, Needs you): its sealed body the artifact's `ask`, `cawco.kind` `artifact` (opening the session with the artifact in its panel at its first pending stop), collapse id `artifact-<artifactId>` so a revision's push replaces it, cleared by a look at the artifact, never a look at the session, and sent whatever else the session waits on. Notices push nothing | **Open** only |
| `CAWCO_ATTEMPT` | An attempt at a task failed | **Open**, **Reply** |
| `CAWCO_TEST` | Settings → Phone → Send test push | none |

A question's own category: categories are registered up front, so the extension, which opens the sealed alert,
registers `CAWCO_QUESTION.<first 8 bytes of SHA-256 of the options, hex>` merged into the registered set and names it
on the push before handing it back. The app prunes, at launch and each time it comes to the front, the question
categories no delivered push names. Three options and Other fill the four actions a category shows.

**Answer and Reply (background).** As Approve below, through `PushActions.perform`: an option reads the ask off
`/api/pending` and sends the label at that index there, Other sends the typed words, both through
`NeedsYouStore.answerQuestion` (the card's Answer), waiting 20 s for `applied`; Reply sends the typed words to the
push's `instanceId` on its `machineId` as the composer's `send` (`SessionsStore.steer`), waiting for `accepted`.
Short of that, a local notification in the push's place: "<name>: answer not sent. <reason> Open to answer."
(`CAWCO_QUESTION`), or "<name>: reply not sent. “<words>” <reason>" with the push's own category, so Reply is there
again; `<reason>` is the hub's refusal (the send record's sentence) when it gave one.

No action label pushes the grant (WORDS.md, Permission/approval): "Approve", never "Allow all" or "Yes". Deny sends the
card's own denial; "Other…" sends the operator's words as the denial's `message`, which the agent reads as what to do
instead. Either, not confirmed in 20 s → "<name>: not denied. <reason> Open to answer." (`CAWCO_PERMISSION_OPEN`).
A push about a session that arrives with the app in front shows as a banner and stays in Notification Centre
(`willPresent` `[.banner, .sound, .list]`).

**Approve (background).** In `userNotificationCenter(_:didReceive:)` with `actionIdentifier == "APPROVE"`, within
the ~30 s the system gives: `GET {hub}/api/pending`, find the envelope whose `requestId` and `instanceId` match the
push and whose `payload.kind == "permission_request"`. Missing (answered elsewhere, or the process ended) → post a
local notification "Already answered." and stop. Found → connect `HubSocket`, send the same `permission.answer`
command `Fleet.answer(_:machineId:.allow)` sends (`resolvePermission`, `behavior: "allow"`, the parked
`updatedInput`), and wait for the ledger's `applied`. Not applied in 20 s → local notification "<name>: not approved.
Open to answer." with category `CAWCO_PERMISSION_OPEN` and the same `cawco` data. Never approve anything but the one
`requestId` the push named.

**Tap / Open.** Default action and `OPEN` route by `cawco.kind`, through the scene's existing navigation:
- `ask` with `instanceId` of a session → open that session with its parked ask card in view (the needs-you queue
  already holds it once the socket syncs; wait for the first `/api/pending` read rather than showing an empty pane).
- `task` → `GET {hub}/api/projects/{projectId}/tasks/{taskId}`, open the project's board with that task's sheet.
- `attempt` → as `task`, scrolled to its attempts; the failed one is `workItemId`.
- `test` → the board.
The app launched cold by the tap reads `launchOptions`/`connectionOptions.notificationResponse` the same way.

**Housekeeping.** When the app becomes active, remove delivered notifications whose ask is no longer in
`/api/pending` (`removeDeliveredNotifications(withIdentifiers:)` keyed by the request's collapse id). Badge stays 0:
the needs-you count belongs to the app's own queue, not to a number pushes would have to keep right.

### 5.8 Decision pages (D21)

- **The source is a program.** A decision page is a `page` artifact (§5.10) whose source is an OpenUI Lang program
  over CawCo's decision library (`@cawco/core/decisions-library`, beside the view library on the one runtime of
  §5.2), written by Caw or any session with the `decision-page` skill and kept in a project at
  `decisions/<name>/page.oui`. The agent never writes form markup: `Decisions(title, children, intro?)` is the page
  (Caw, "N of M picked", Send picks), `Section(title, children)` a heading over some decisions,
  `Decision(id, question, options, why?, media?, after?, multiple?)` a card in the kit's recipe, `Option(id, label,
  line?, recommended?, media?)` an option; Text, Badge, Row and Column are the view library's. A component the
  library does not have is dropped and named, never drawn. One artifact in the panel: the person picks, pins and
  inks on it as on any page, and each pick is kept in the artifact's `state` by decision id with the program's hash.
- **Media, anywhere.** On an option, on a decision between its why and its options, or between decisions:
  `Image(file, alt, caption?)` (a file beside the program or a `generate_image` result, kept with the page),
  `Diagram(mermaid, caption?)` (any Mermaid type, drawn by Pele on the house tokens, re-laid for the width it has;
  "Open as canvas" for the types `@excalidraw/mermaid-to-excalidraw` draws as elements: flowchart, sequence, class,
  state, ER), `Canvas(artifact, caption?)` (a canvas of the session's, live and read-only), `Preview(artifact,
  caption?)` (another artifact of the session's, live: a page such as an animated mockup in HTML on the page's
  own origin, a dev server's preview or a sheet on an origin the hub opens for it; Open to draw brings a Canvas to
  the panel), and `Dials(name, config)` (a DialKit panel at the page's foot, made by the kit's dials.js as on an
  HTML page, writing `state.dials`). A piece whose artifact is gone says so in words.
  Custom content, never custom code: a drawn thing none of these expresses is a canvas or an HTML page shown with
  Preview. `Mockup` (one story of a sheet on the stage) waits for the sheets and stage redesign.
- **Where it renders.** A project's page is served on the project's own preview origin, at `/__cawco/page/<id>/`,
  one origin for the project's life whichever session wrote the page and whether it still stands: the writer's
  panel, the Decisions tab, Files and the app all load it there (a page outside any project, on its session's). An
  embed on it (a Preview of a dev server or a sheet) may be framed by exactly the origins the page was served on.
  The hub serves a host page at that address, inside the panel's iframe (the pane, the
  iOS web view and the own tab unchanged): the renderer and the decision library bundled by the hub, the program in
  the page, the overlay's tag carrying the program's sha256 as the page hash. A revision is
  `artifact_update(id, statements)`: the changed statements merged by name with lang-core's `mergeStatements`; the
  host page draws the new program in place and tells the overlay (`cawco:hmr`), so picks, notes, pins and ink stay
  on their cards (each card carries `data-cawco-choice` and `id="decision-<id>"`). The update answers what it
  changed, never the whole page, and names what it left broken: a picked decision or option it took out (the pick
  is kept), a decision it lacks that another page comes `after`, an `after` naming no decision. Any session of the
  project, Caw included, reads a page's program with `artifact_read` and revises it; a link is one re-emitted
  `Decision` statement with `after` set.
- **HTML when a pick is not an option.** A page is written as HTML on the kit only when the person places or
  operates something to decide (a point, a sample dragged into shape, `cawco.pickPlace`); the hub keeps its DOM card
  reader for that case alone. Same artifact kind, state keys, tab, record and Make tasks.
- A **Decisions tab** lists pages with progress ("12 of 20 picked"). "I'm done picking", or sending a comment, wakes
  the session that wrote the page, or Caw if it has ended.
- **Make tasks** runs to-tasks over the picks and notes, reading the cards from the program; each task links back to
  its card (`decided: <page>#<card>`); the page writes a short decision log so later sessions read why.
- **Links between pages are derived.** A decision whose `after` names another page's decision (`page#card`) links
  the two pages; the tab's list says it as words on each page's row ("After: …", "Unlocks: …"), each opening that
  page (the owner's pick of 10-24, "A list, links as words on the cards", which replaced the decision graph).
  `decisions.json` and `decision_add`, `decision_link` and `decision_group` are gone; the writer edits the
  program. The cards come from each page's `page.oui` in the project's folder; picks from the artifact. **A project's page is the project's:** its name is unique
  in the project, so another session's create of that name revises the same page, picks kept; its artifact lives
  as long as its source in the folder, not as long as the session that wrote it (a deleted session leaves it with
  no session), and goes when that source leaves the folder (artifact_delete takes both, in one commit) or the
  project goes. A `page.oui` the hub holds no artifact for (written to the folder, never published) draws its cards
  unpicked, said so under the graph, as is each `after` naming no decision (the page and card it names) and each
  orphaned pick; a card whose picked option a revision took out keeps the pick and says its option is gone, and on
  the page it stands open, not picked.

### 5.10 Artifacts (D22–D27)

Owner session 2026-10-13, grilled over two rounds; the task is tsk-4, with tsk-3 (preview comments and the canvas
panel) under it. This section supersedes §5.7 "Canvas" and the surfaces of D18–D20; D19's store and D20's comment
semantics continue inside it. DESIGN.md "Artifact panel, canvas and ink" decides every pixel; WORDS.md carries the
terms.

**One concept.** An **artifact** is a document a session made that you work in, kept by the hub per session. Three
kinds: a **page** (HTML the agent wrote: a decision page, a form, a mockup), a **canvas** (an Excalidraw drawing by
you or the agent) and a **preview** (a dev server or folder shown live through the existing proxy). One store, one
overlay, one bridge and one panel serve all three; a project's artifacts are the same panel at project scope. The
surface §5.7 asked for (states and screens on a graph) is the **component canvas** below (2026-10-19): a
component's real instances on a pannable, zoomable canvas the stage serves, its map drawn on Svelte Flow.

**The document (D23).** One Yjs doc per artifact, which the hub syncs (the y-websocket protocol over the preview
listener) and persists as its update log in hub SQLite; every view of the artifact (the panel, the iOS web view, a
tab of its own) opens the same doc and converges. Its maps:
- `state`: every page field by its `name` or `id` (input, select, textarea, contenteditable) plus picks, notes and
  dials; `data-cawco-choice` stays for custom widgets. Keys outlive revisions, as picks do today.
- `elements`: the canvas, bound with `y-excalidraw` (element-level last-writer-wins by `version` and `versionNonce`,
  Excalidraw's own `reconcileElements` rule; an element being edited locally is never overwritten).
- `ink`: stroke groups, each naming the elements it encloses or crosses (`over`) and stored relative to the box
  of the one anchoring them (their container when it is not much bigger, else the first), with its page
  coordinates and the anchor's selector and source.
- `comments` and `pins`: tsk-3's design (numbered pins, comment cards with replies, resolve and reopen).
The agent reads a JSON snapshot (state, pins, comments, and for a canvas the **outline**) and writes JSON patches,
applied as one Y transaction. A write that lands on an element you changed since the agent last read is applied and
flagged in the tool's result. The doc survives closing the panel, a refresh and a device change.

**Live updates.** The agent re-publishes a page and the overlay morphs the live DOM with idiomorph (`restoreFocus`,
the active field's value kept): focus, scroll, typed values and bound fields survive, as hot module reload keeps
state. A canvas changes in place through the Y binding; it never reloads. A morph or a remote element change waits
for pointer-up and field blur, so nothing moves under a hand. A dev-server preview keeps its own HMR.

**Delivery to the agent.** Changes batch into one message after 3 s of quiet (`--dur-wait-grace` × 3), and go at
once while the session's turn is running, so an agent mid-conversation sees you answering as it goes. Send ("Send N")
still says "that's all" for picks: it carries the unsent picks and the note. Pins and comments never wait for it
(decision log 2026-10-23).

**Its own tab.** "Open in a new tab" opens the dashboard's artifact route with the panel's full chrome and the same
doc, never the raw proxied page. The overlay's transport is one seam: the parent window (iframe), the WebKit handler
(iOS), or a direct hub socket (a tab of its own).

**The panel.** Every session has an artifact panel: the preview sheet's recipe (beside the transcript on wide screens
and iPad, the drawer on phones), listing the session's artifacts newest first, its head carrying the open artifact's
name as the title control (the Claude-panel reference) with Open in new tab, Dock/Undock, Share, and Close. Inside a
project, the agent can escalate an artifact into the repository at `artifacts/<name>/` (the doc's files and a
snapshot), git-versioned like decisions.

**The canvas (D24, D25).** `@excalidraw/excalidraw` in the overlay's host page with its own chrome hidden and our
tool rail over it on house tokens. iPad: Excalidraw's pen mode (finger pans, pencil draws, pressure recorded);
elsewhere a tool is picked and drawn with. **Shape recognition is ours and in v1:** hold the pencil still at the end
of a stroke for `--dur-press-hold` and the stroke snaps to a line, arrow, rectangle, ellipse or triangle (the shape
element replaces the freedraw element), as Notes and Freeform do. The agent reads an **outline** (one line per
element: id, type, text, box, arrow bindings; ink collapsed to a count and what it sits over) plus a PNG; it writes
skeleton elements (`convertToExcalidrawElements`) or Mermaid (`@excalidraw/mermaid-to-excalidraw`); the
`.excalidraw` file is the truth. A send carries the file, the outline and the PNG through the existing
`attachments`/`images` contract. The pen swipe makes a **draft** canvas; the first send makes it an artifact the
agent holds; the agent creates and edits canvases on its own.

**Entrances and motion (D26).** A pen swipe up on the composer (the iPad app, and the web on any pen device) opens a
canvas; touch type decides, so a finger's swipe stays the recall wheel and the pencil is removed from the wheel's
recognizer. Also Attach → Draw, ⌘⇧D on the web, and the panel's +. The pill keeps its three boxes. The pill grows
out of its top edge as it does for the wheel and keeps going until the canvas stands above the field, **the field
staying below to type**; its top edge drags to resize (floor 40 % of the column). **Dock** sends it to the side as
the preview tool stands, a shared-element flight; the field gives its room back on the composer's clock. Done folds
it back into a chip; Send flies the chip into the transcript row. A phone has no swipe: Attach → Draw, the morph to
the window's height, Dock to the drawer.

**Ink on any artifact (D27).** Ink lives in the overlay for every platform: an SVG layer in the page's document,
strokes rendered with `perfect-freehand` from Pointer Events (`pointerType: "pen"`, `pressure`, tilt; coalesced and
predicted events for smoothing). Pencil draws at once, a finger scrolls and taps, the pencil's double-tap toggles the
eraser; Comment mode (tsk-3's Select → Comment, key C) stays for taps. After a stroke, an icon stands at its end;
press-and-drag opens a radial menu of four: **Annotate** (a numbered pin on the elements under the ink, no note),
**Comment** (a pin with a thread, stored at once), **Illustrate** (ink kept as a drawing, bound to nothing, sent as a
picture), **Erase**. Ignored ink is an illustration on the next Send. Ink is re-anchored by selector after a
revision; unplaceable ink goes to the comments' "moved" tray. The selection chip, its popover and `selection.md` are
deleted (tsk-3).

the page posts a render report (drawn, empty, failed, unseen; box, words, component chain, each forced state's
computed-style delta), which the stage keeps per states file and every tool answers from; with no panel open the
daemon draws it in the machine's own Chromium. `design_map` is the library the agent builds from (used in and
made of from the frames' chains and the imports): parts are mounted, never redrawn. The `component-canvas` skill
is the loop: map, write, open with `about`, read what was drawn, check it reads, show, take the tuning back into
code.
Tokens stay the project's; a prop typed with the design system's generated `TokenColor`, `TokenSize` or `TokenFont` is offered its names in the inspector.
A project whose toolchain takes no plugin (Next.js, Angular CLI, plain webpack, custom servers, Flutter, SwiftUI,
Compose) shows its components as an
HTML `page` artifact that loads the project's built CSS, with picks, pins and ink, and no `file:line`. A project with
no code yet starts as real code from the first screen: the stack is named once and the agent scaffolds it with the
framework's own tool. This replaces the OpenUI mockup library (2026-10-15) and the dev-server-or-folder preview as
the way an agent shows a component; `preview` remains for whole apps. No CawCo design format, no recreation of
existing components.

### 5.11 Browser take-over (D30)

Owner session 2026-10-18. When an agent needs the person in a page (a sign-in, a one-time code, a CAPTCHA, a payment, a consent only they may give), the person acts in that agent's own browser, same cookies and same page, from the preview panel on the web dashboard and in the iOS app, and nothing they type or see during that time reaches any agent by any route. When they hand back, the agent carries on signed in, and the sign-in lasts for the project. DESIGN.md "Artifact panel" and the new "Browser view" recipe decide every pixel; WORDS.md carries the terms.

- **One browser per project.** A project has one browser on the machine of the session that first needs it: a container (`ghcr.io/m1k1o/neko/chromium`, our image on top of it) with its Chromium profile on a named volume of its own (`cawco-browser-<key>`), nothing shared across projects. Its key is `project:<projectId>`; a session outside any project uses `machine:<machineId>`, one per machine, whose sign-ins last for that machine. It starts when a session's browser tool first connects, or when the person opens it; it stops (container stopped, volume kept) after 30 minutes with no agent connection and no viewer, and wakes on the next need. Forgetting a project removes its container and volume; the Forget tray says so. A project that runs on a second machine gets a second browser there: sign-ins last per project per machine, since a profile is one machine's files.
- **A machine without a container runtime** runs the same browser as a local Chromium (Playwright's build, headless), one process per key with its profile in the daemon's state dir, behind the same gate and the same shield; onboarding and the view name the install (Docker, OrbStack or Colima on a Mac; Docker Engine or Podman on Linux) and the browser moves into a container the next time it starts after one is found. Its take-over streams one page over CDP (frames out, input in) through the hub's socket; the rest of the browser's pages are not on screen there, and the band says so.
- **A window per session.** A Chromium profile is one process, so a project's sessions share its browser. Each session's pages open as windows of their own, and each session sees and drives only its own pages: CawCo's gate scopes every DevTools connection to the pages that session opened. A take-over brings the asking session's current page to the front.
- **The gate.** No session reaches Chromium's DevTools port. Each session's browser tool (chrome-devtools-mcp) connects to the daemon's gate on the machine with that workspace's own token; the gate scopes targets, refuses the calls that would end the browser, read or clear its cookies, open a `chrome://` page, or touch another session's pages, and is the one thing the shield cuts.
- **A browser ask.** The agent calls `browser_ask` with one sentence of reason and the page's origin; it lands in Needs you, in the session's transcript as a card, and on the phone as a push, and the tool waits. Take over opens the browser in the panel with that page in front and starts the private period; Decline answers the tool with the person's words. The person can also take over unasked, from the panel.
- **Private.** From Take over to Hand back: every agent connection to the browser is cut and new ones refused with one sentence; the person's input goes to the browser and nothing else; the clipboard is theirs; no screenshot, DOM, accessibility tree, network body, injected script, `Runtime.evaluate` or cookie read exists for any agent, in this session or another of the project. Hand back is the person's act: the button, or every view of the take-over closed for 2 minutes. At hand-back the daemon takes control away from the viewer, loads the current page again by GET (nothing typed survives in a field), empties the browser's clipboard, then reopens the gate and answers the tool with the page's origin and nothing else. The browser saves no history, and Chrome never saves or fills passwords, addresses or cards; an agent's connection can never read or clear the browser's cookies (it uses the sign-in, it never holds it; a signed-out test is a new browser context).
- **Reaching the stream.** Signaling and neko's REST go through the hub on the dashboard's own origin (`/ws/browser/...`), authorised as every dashboard socket is: no neko password screen, no second sign-in. The media is standard WebRTC (RFC 8835: full ICE, UDP first, TCP beside it, TURN for what blocks both): neko runs full ICE with one UDP and one TCP port per browser published on the browser's machine, advertising the machine's own addresses (LAN and tailnet connect directly), and the fleet's **stream relay** in its ICE server lists, so a screen on cellular data, behind a strict firewall or on a web-only tunnel connects through the relay. The hub mints each viewer a short-lived relay credential (TURN REST API scheme) and puts it in the offer it relays; the browser's own relay credential is minted when it starts. Without a relay, a direct way is still tried; when ICE fails the view says so and points to the relay step.
- **The stream relay** is coturn, run by the agent as a container on the runtime's media network on a fleet machine with a public address, picked once in onboarding (Settings › Browsers afterwards): one listener on UDP and TCP 443, the only ports it publishes or asks the router for; its UDP relay range stays inside its container, every relayed stream relay to relay inside the one coturn; with a DNS name given, the same listener also answers TURN over TLS on 443 with a Let's Encrypt certificate the step obtains, which networks that allow only real HTTPS need. The hub keeps the shared secret; the relay's health (a STUN binding answered on each port) shows in Settings and on the step. Ports it cannot bind are named with the fix.
- **Overhead.** neko encodes only while someone watches; an idle browser costs its RAM. The build's first item measures start time, idle RAM, Mac CPU while watching and phone latency on a two-machine rig, and the numbers decide resolution, frame rate and idle-down.
- **The view** is a `browser` artifact, listed in the panel of every session of the project (and of the machine's sessions, for the machine browser), shown by a browser ask or by the person. Its head is the artifact panel's; under it an address band shows the page's origin and who has control; the well is the stream. States: starting, live (agent driving), you have control (private), disconnected, asleep, stream not connected, machine away, runtime missing (the local browser's band line).
